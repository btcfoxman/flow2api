## 原因与修复范围

1. 多个队列 worker 先进行不占用账号的可用性预检查，实际生成入口再原子保留账号/代理与积分。两个检查之间账号可被其他 worker 占用；原代码把第二次分配失败写成 503、失败进度 100，再将状态改为 `retrying`。
2. 对尚未进入计费提交的排队请求，用专用内部 `AsyncQueueDeferred` 信号回到 FIFO 等待，不创建生成失败日志/计数、不增加真实提交重试次数。保留原 payload、位置与截止时间。
3. 普通同步调用的无账号响应仍为对外安全的 503；具体调度原因仅保存在管理员日志，不返回调用者。
4. 确实发生的 429/503 重试保留状态码与原始错误证据，但进度为 0；轮询终态失败不转换为重试。
5. 列表按稳定公开队列任务 ID 关联后续结果，已有结果记录时不重复显示旧重试尝试。原始日志未删除，详情仍可查询；历史 `retrying / 100%` 展示修正为 0%，标明“提交重试记录、非最终生成结果”，未分配账号不再显示“未知”。
6. 会话验证刷新余额、启用状态或模型档位后，再校验候选账号；交互登录暂停的账号不进入可用性预检查。

不自动降低分辨率/时长、不启用停用账号、不将未确认提交自动重放。排队超时照常结束；资源不足仍需补充符合请求成本的可用账号或由调用者主动选择低成本模型。
