## 根因与修复

1. 调度、余额刷新和显式验证各自调用浏览器账号快照，缺乏跨入口的进行中请求合并。
   现在按账号 ID 和凭据版本合并正在进行的探测；不同 Cookie、代理或账号不共享。
   不缓存余额查询结果替代真实刷新，也不省略操作员主动发起的重新验证。
2. 调度在锁外检查会话可用，但等待锁后可能已被其他请求判定失效。
   现在在锁内重新读取账号，检查启用状态、凭据版本和会话状态；旧候选不会继续探测或拒绝新凭据。
3. 后台刷新只在整轮开始时筛选账号，等待并发信号量期间发生的删除、禁用和会话失效未被复查。
   现在拿到并发名额后再次读取和判断，跳过项计入 `skipped`，不计为探测失败。
4. 启动时运行态验证记录为空，数据库默认最久未使用优先，导致旧失效账号阻塞近期可用账号。
   现在只重排尚无验证记录的 Flow 候选，让近期使用过的账号优先接受真实预检。
   `last_used_at` 仅是探测优先级提示，不是成功证明或授权有效期；已观察账号和 Labs 账号的相对槽位保持不变，
   正常轮询、并发额度、积分预占、账号排除和代理冷却规则不变。
5. 第一阶段上线后，实测定位到浏览器名额竞争：已验证账号 52 等待启动浏览器时，
   后到的后台探测仍可抢占刚空出的名额。补充引入 FIFO 浏览器启动名额队列，
   后到请求不能插队；已经运行的账号直接复用，不排在等待新浏览器的请求后面。
   只淘汰空闲浏览器，仍遵守原有 3 个浏览器上限；取消、启动失败和关闭服务都会释放排队位置。

共享探测具备等待者计数：一个调用方取消不会取消其他调用方的探测；最后一个调用方离开时取消并等待清理。
删除账号会取消其进行中的探测，避免退出后遗留浏览器工作。
