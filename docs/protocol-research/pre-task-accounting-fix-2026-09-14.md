# 3.5 pre：提交不确定、诊断及任务计数修复

## 修复范围

2026-09-14 的只读分析发现，`MZZa6b` HTTP 200 的不可识别响应被转换成提交不确定，同时错误地累计账号连续失败。部分排队任务的内部 503 尝试也进入了最终失败统计。此次先修复这两项可确认的本地问题，并补充下一轮上游分析所需的安全证据。

- `AngularProtocolError`（包括 `AngularSubmissionUncertain`）不作为账号禁用计数依据；主异常路径保留异常类型，轮询连续协议异常也保留免计数标记。
- 不取消不确定提交的防重提保护，不切换账号重发，不解除真实 HTTP 429 的出口冷却。
- RPC 诊断保留解析失败分类、响应字节数、帧数、匹配行数和有界类型结构。结构只包含类型和数量，不包含任何标量内容、对象键、Cookie、签名链接、提示词或原始响应。
- 媒体失败保留 `wire_status` 4/5/7；兼容层的 13/1 明确标为 `local_normalization`，不再称为上游原始错误码。未知字段不猜测业务语义。
- 入队前能力拒绝新增 `generation_capability_rejected`，只记录已知模型和固定阶段/原因，不计入已接收任务。

## 计数方式

新增 `async_generation_outcomes`，以公共任务 ID 为主键。仅新接收的队列任务建立 pending 记录；队列失败（包含过期、提交结果不确定和崩溃恢复失败）及公共任务最终状态在同一个 SQLite 事务中更新终态。

`queue_submission_guard` 通过任务局部上下文关联提交及后台结果日志，内部 429/503 尝试标为 `retrying`。这些日志不再独立生成 outcome，避免与公共任务重复。成功数必须等公共任务 completed；排队和上游刚接收均不是成功。

清理队列、重复终态更新、清理请求日志及重启不会增加第二次计数。未接受的队列满拒绝也不进入任务台账。非队列请求保持旧日志台账兼容。

历史日志缺少稳定公共任务关联，因此**未重写历史累计数**，也未批量重置账号错误次数或启用既有禁用账号。Prometheus 的请求尝试指标仍是请求指标，最终用户任务数量应使用合并后的 outcome 接口。
